## 6. معماری پیشنهادی

### 6.1 نمای کلی

```text
[Flutter Client: Mobile/Desktop]
              |
     [Platform Media Adapter]
              |
       [Media Transport]
        WebRTC / HTTPS
              |
       [Session/API Service]
        Node.js + TypeScript
              |
       [Realtime Orchestrator]
         /       |        \
        /        |         \
 [Speech/ASR] [Translation] [Voice/TTS]
        \        |         /
         \       |        /
       [Timestamp & A/V Sync]
                 |
        [GPU Lip-Sync Worker]
             Python/PyTorch
                 |
        [Output / Playback]
```

این نمودار مفهومی است؛ پیاده‌سازی دقیق انتقال ویدیو و صدا باید بر اساس نرخ فریم، پهنای باند، تأخیر و APIهای سرویس‌های منتخب تعیین شود.

### 6.2 کلاینت‌ها

پیشنهاد اولیه برای رابط کاربری مشترک: **Flutter**. رابط کاربری و بخش زیادی از منطق نمایش می‌تواند مشترک باشد، اما ضبط رسانه و پخش کم‌تأخیر باید از طریق افزونه‌ها یا ماژول‌های بومی Android، iOS، Windows و macOS انجام شود.

مسئولیت‌های کلاینت:
- مدیریت مجوزها و انتخاب منبع رسانه.

پیشنهاد: **Node.js + TypeScript** برای API و هماهنگ‌کننده نشست‌ها.

مسئولیت‌ها:
- احراز هویت و مدیریت کاربران.

- مدیریت تنظیمات زبان، صدا و قابلیت‌ها.

در نسخه اولیه بهتر است به‌جای ساخت تعداد زیادی میکروسرویس، یک **سرویس ماژولار** ساخته شود و فقط پردازش GPU در یک worker جداگانه اجرا شود. جداسازی بیشتر زمانی انجام شود که مقیاس یا نیاز عملیاتی آن را توجیه کند.

### 6.4 لایه هوش مصنوعی

برای جلوگیری از وابستگی به یک فروشنده، برای هر قابلیت یک رابط داخلی تعریف شود:

- `SpeechRecognitionProvider`
- `TranslationProvider`
- `VoiceSynthesisProvider`
- `VoiceProfileProvider`
- `LipSyncProvider`

هر ارائه‌دهنده باید وضعیت، زمان پاسخ، هزینه تقریبی، زبان‌های پشتیبانی‌شده، محدودیت نرخ، خطا و امکان لغو درخواست را گزارش کند. نام مدل‌ها و APIهای دقیق باید هنگام اجرا و بر اساس مستندات رسمی و آزمایش واقعی انتخاب شوند؛ نباید نام مدل یا پشتیبانی زبان بدون راستی‌آزمایی در کد ثابت شود.

### 6.5 پردازشگر هماهنگ‌سازی لب

- سرویس جداگانه Python با PyTorch و در صورت نیاز GPU.
- دریافت شناسه نشست، فریم‌ها یا کلیپ مجاز، صدای ترجمه‌شده و زمان‌مهرها.
- اجرای مدل هماهنگ‌سازی لب و بازگرداندن فریم/قطعه ویدیویی همراه با زمان‌بندی.
- محدود کردن طول صف برای جلوگیری از افزایش بی‌پایان تأخیر.
- امکان غیرفعال کردن خودکار این مرحله در صورت ازدحام یا ناتوانی در رسیدن به زمان هدف.
- پایش مصرف VRAM، زمان پردازش هر قطعه و کیفیت خروجی.

مدل‌هایی مانند MuseTalk یا LatentSync می‌توانند گزینه‌های تحقیق و نمونه‌سازی باشند، اما قبل از انتخاب تولیدی باید مجوز، نیاز سخت‌افزاری، کیفیت، تأخیر و سازگاری آن‌ها با سناریوی واقعی بررسی شود.

### 6.6 انتقال رسانه و همگام‌سازی

- استفاده از WebRTC برای انتقال بلادرنگ در سناریوهایی که مناسب است.
- استفاده از WebSocket برای پیام‌های کنترلی، وضعیت نشست و رویدادها؛ WebSocket به‌تنهایی جایگزین کامل انتقال رسانه نیست.
- استفاده از HTTPS برای APIها و فایل‌ها.
- نگهداری زمان‌مهر برای متن، صدای اصلی، صدای ترجمه‌شده و ویدیو.
- استفاده از بافر تطبیقی برای جلوگیری از پرش و ناهماهنگی.
- پایش تأخیر شبکه، تأخیر مدل‌ها، زمان صف و زمان نهایی پخش.

- هدف اولیه را بر اساس آزمون واقعی تعیین کنیم؛ تأخیر چندثانیه‌ای ممکن است برای بعضی سناریوها اجتناب‌ناپذیر باشد.
- در صورت عقب افتادن ویدیو، حالت جایگزین صدای ترجمه‌شده بدون هماهنگ‌سازی لب در دسترس باشد.
- کیفیت ترجمه، شباهت صدا و طبیعی بودن لب‌خوانی باید جداگانه ارزیابی شوند.

## 8. امنیت، حریم خصوصی و رضایت

- گرفتن مجوز روشن و قابل فهم پیش از ضبط میکروفون یا رسانه.

- نگهداری کلیدهای API فقط در سمت سرور؛ هرگز آن‌ها را داخل برنامه کلاینت قرار ندهید.
- حداقل‌سازی ذخیره صدا، تصویر و متن؛ ذخیره‌سازی باید اختیاری و با توضیح روشن باشد.
- تعریف مدت نگهداری، حذف نشست و درخواست حذف داده‌ها.
- محدود کردن دسترسی کارکنان و ثبت دسترسی‌های حساس.
- استفاده از نمونه صدای افراد فقط با رضایت یا مجوز معتبر.
- عدم ضبط پنهانی یا دور زدن کنترل‌های امنیتی برنامه‌های دیگر.
- بررسی قوانین حریم خصوصی، حق تصویر و صدا و الزامات هر کشور و فروشگاه برنامه پیش از انتشار.

## 9. فناوری‌های پیشنهادی

| بخش | گزینه پیشنهادی اولیه | ملاحظات |

## 11. محدوده نسخه اولیه (MVP)

### داخل محدوده MVP

- کلاینت اولیه با Flutter.
- انتخاب زبان مبدأ و مقصد.
- دریافت میکروفون و پردازش فایل صوتی/ویدیویی انتخاب‌شده توسط کاربر.
- تبدیل گفتار به متن، ترجمه به فارسی و تولید صدای ترجمه‌شده.
- پخش صدا و نمایش زیرنویس.
- سرویس مرکزی با احراز هویت ساده، مدیریت نشست و ثبت خطا.
- رابط‌های قابل تعویض برای سرویس‌های هوش مصنوعی.
- اندازه‌گیری تأخیر و هزینه هر نشست.
- مستندات روشن محدودیت‌های پلتفرم.

### خارج از محدوده MVP

- تضمین دریافت صدای تمام برنامه‌های دیگر.
- تزریق صدای ترجمه‌شده به تمام تماس‌های WhatsApp، Telegram، Zoom یا سایر برنامه‌ها.
- هماهنگ‌سازی لب برای هر نوع ویدیو و هر تعداد چهره با تضمین کیفیت.
- پشتیبانی هم‌زمان از تمام پلتفرم‌ها در سطح تولیدی.
- آموزش یا fine-tune اختصاصی مدل‌ها قبل از اثبات نیاز و امکان‌پذیری.
- ضبط دائمی یا ذخیره پیش‌فرض رسانه خام.

### مرحله دوم

- آزمایش دریافت صدای پخش‌شده در Android برای برنامه‌هایی که اجازه می‌دهند.
- پشتیبانی از چند منبع ورودی و دستگاه‌های صوتی.
- بهبود ترجمه قطعه‌ای و کنترل تأخیر.
- حساب کاربری، سهمیه و گزارش مصرف.

### مرحله سوم

- نمونه اولیه هماهنگ‌سازی لب روی ویدیوهای مجاز و از پیش انتخاب‌شده.
- worker پردازش GPU، صف محدود و بازگشت خودکار به حالت صوتی.
- ارزیابی کیفیت ویدیو، زمان پردازش و مصرف VRAM.

### مرحله چهارم

- توسعه adapterهای مستقل برای Windows، macOS و iOS بر اساس APIهای واقعی هر پلتفرم.
- بررسی ادغام‌های رسمی برای تماس‌های زنده، در صورت وجود.
- آماده‌سازی برای مقیاس‌پذیری، پرداخت، پایش و انتشار عمومی.

## 12. معیارهای پذیرش

## 13. ریسک‌ها و پرسش‌های فنی باز

- آیا صدای انتخابی می‌تواند با کیفیت قابل قبول فارسی تولید کند؟
- آیا API انتخاب‌شده خروجی قطعه‌ای و کم‌تأخیر می‌دهد؟
- چه میزان تأخیر برای سناریوی هدف قابل قبول است؟
- کدام پلتفرم در نسخه اول بیشترین ارزش را ایجاد می‌کند؟
- آیا نیاز اصلی ترجمه ویدیوهای تماشا‌شده است یا ترجمه تماس زنده؟
- آیا ویدیو باید درون خود برنامه پخش شود یا قرار است خروجی به برنامه دیگری منتقل شود؟
- چه مقدار پردازش می‌تواند محلی باشد و چه مقدار باید در سرور انجام شود؟
- هزینه هر دقیقه ترجمه صوتی و ویدیویی چقدر خواهد بود؟
- مجوز نرم‌افزارها و مدل‌های متن‌باز انتخابی برای استفاده تجاری چه محدودیت‌هایی دارند؟

## 14. تصمیم معماری پیشنهادی

پیشنهاد می‌شود پروژه با این اصول آغاز شود:

1. **یک سرویس مرکزی و قرارداد API مشترک** برای نشست‌ها و ارائه‌دهنده‌ها.
2. **یک رابط Flutter مشترک** برای کاهش هزینه توسعه UI.
3. **adapter رسانه مخصوص هر پلتفرم** برای رعایت محدودیت‌های واقعی سیستم‌عامل.
4. **Node.js + TypeScript** برای API و هماهنگ‌سازی نشست.
5. **Python + PyTorch** فقط برای worker پردازش تصویر و هماهنگ‌سازی لب.
6. **طراحی قابل تعویض ارائه‌دهنده‌ها** برای تشخیص گفتار، ترجمه، تولید صدا و lip-sync.
7. شروع با **فایل صوتی/ویدیویی و ترجمه صوتی**، سپس دریافت صدای برنامه‌های دیگر در پلتفرم‌های مجاز و در نهایت هماهنگ‌سازی لب بلادرنگ.
8. **عدم وعده سازگاری با همه برنامه‌ها** تا زمانی که هر سناریو روی دستگاه واقعی آزمایش نشده باشد.
9. **حریم خصوصی، رضایت و کنترل هزینه** به‌عنوان نیازهای اصلی محصول، نه قابلیت‌های بعدی.
